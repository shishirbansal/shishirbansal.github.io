Salesforce Architecture April 1, 2026

Salesforce Licenses

A practical guide to how Salesforce licenses actually work: platform licenses, user licenses, permission set licenses, editions, add-ons, and the license families most architects keep comparing in real org design.

How to read this guide

Concept first, family second, user access last

  • Start by deciding what level the requirement belongs to: org-wide platform capability, user-level access, or user-level extension.
  • Then identify the user type: internal employee, external user, Chatter-only collaborator, or industry-specific role.
  • Use license families as the filter, then compare the exact features needed such as CRM objects, files, reports, dashboards, or community access.

How Licenses Work

Trailhead concept model, reduced to the parts that matter most

Platform license

Org-level capability

Defines functionality for the org as a whole. Think of this as what the environment can support before you decide which individual users get what.

User license

One per user

Each user gets one user license. That license establishes the core functional boundary for that person’s role in the org.

Permission set license

Add extra capability

Used to extend a user beyond the base user license. A user can have multiple permission set licenses when extra product capability is needed.

Editions, Add-ons, and Settings Licenses

The packaging model Trailhead clarifies well

Settings licenses Platform + User + Permission Set

These are the building blocks that describe functionality.

→
Product licenses Editions + Add-ons

These package the settings licenses into something customers actually purchase.

→
Real-world choice Buy the package, assign the access

Architecturally, you design from user need backward into the edition and add-on mix.

  • An org has one edition license that establishes the main baseline of functionality.
  • An org can have multiple add-ons or none at all.
  • You do not buy individual permissions directly; permissions and preferences are bundled into licenses.

License Families At A Glance

The clearest grouping visible in the PDF

Identity licenses

Used when identity, authentication, and controlled access matter more than full CRM usage.

  • Knowledge Only: users who only need access to Salesforce Knowledge content.
  • Identity: internal identity-focused access with authentication and app access control.
  • External Identity: identity services for users outside your organization.

Chatter licenses

Used for collaboration-first users who may need varying levels of files, feeds, groups, and limited data access.

  • Chatter External
  • Chatter Free
  • Chatter Only
  • Employee Apps Starter

Core internal licenses

Used for standard CRM and service workflows for employees inside the business.

  • Lightning CRM
  • Sales Cloud
  • Service Cloud
  • Employee Apps & Community

External and industry licenses

Used when access is community-facing or tailored to a specific vertical solution.

  • Partner Community
  • Customer Community
  • Financial Services Cloud
  • Health Cloud

What The PDF Compares

Useful comparison dimensions called out directly in the source license board

Chatter capability checks

  • Desktop client and Salesforce mobile app access
  • File sharing, groups, and feed participation
  • Topics, hashtags, and global search visibility
  • Custom objects, accounts, contacts, and calendar coverage
  • Reports, dashboards, tasks, and activities

Product/solution coverage

  • Which standard objects the license family is oriented around
  • Whether it is meant for internal users or external/community users
  • Whether it maps to a core cloud, a community model, or an industry package
  • How much platform customization and object access the user is expected to need

Provisioning and Sandbox Notes

The operational detail that is easy to forget during design

Provisioning applies when

  • You make an initial Salesforce purchase and the org is activated.
  • You purchase an upgrade or add-on.
  • A license definition changes as part of a Salesforce patch release.

Environment caveats

  • Provisioning applies to production orgs, not automatically to every sandbox.
  • Sandbox license state can require refresh or matching production licenses to stay aligned.
  • Demo, Developer, Scratch, and Trial orgs behave differently from production licensing flows.

Practical Selection Guide

Choose by user role, not just product name

Use identity licenses when

  • The main job is authentication, access management, or app entry.
  • The user does not need broad CRM object access.
  • You want external identity without a full Salesforce user footprint.

Use Chatter licenses when

  • The main job is collaboration, file sharing, feeds, and lightweight participation.
  • The user needs communication access but not a full sales or service seat.
  • You are deciding how much limited record visibility is appropriate.

Use internal CRM licenses when

  • The user works directly in sales, service, or operational CRM processes.
  • Standard objects, reports, dashboards, and process automation matter.
  • The role is an employee role, not an external community user.

Use external/industry licenses when

  • The audience is partner, customer, or portal-based.
  • The experience is community-driven rather than employee-driven.
  • The org uses a vertical cloud like Financial Services Cloud or Health Cloud.

Quick Memory Model

A fast way to think before you compare details

  • Edition: the main product package the org runs on.
  • Add-on: the optional package that extends the org.
  • Identity: who can get in and how.
  • Chatter: who can collaborate and share.
  • Core CRM: who can work inside the business process.
  • Permission Set License: extra capability layered onto a user.
  • Community / Industry: who needs access outside the employee model or within a specialized cloud.
